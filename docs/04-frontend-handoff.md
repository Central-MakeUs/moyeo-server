# 프론트 전달사항

외부 API 점검 중 확인한 프론트 변경 요청을 항목별로 누적한다.
백엔드 API 계약을 기준으로, 아래 항목의 프론트 적용 요청을 정리한다.

## 1. 카카오 로그인 실패 안내 구분

- 대상: `POST /api/auth/kakao` 실패 안내
- 상태: 전달 준비 / 프론트 미적용
- 확인 기준: 2026-11-02, 프론트 `develop`의 `438dd791` 커밋 정적 점검

**현재:** 소셜 로그인 공통 오류 분류에서 타임아웃만 구분하고, 401·503은 같은 문구로 안내한다.

**요청:** Axios의 `error.response.status`와 응답 `code`로 인증 실패와 서비스 이용 불가를 구분한다.

| 응답 | 현재 안내 | 변경 요청 |
| --- | --- | --- |
| `401 SOCIAL_LOGIN_FAILED` | 로그인에 실패했어요. 잠시 후 다시 시도해 주세요. | 로그인을 완료하지 못했어요. 다시 로그인해 주세요. |
| `503 SOCIAL_LOGIN_UNAVAILABLE` | 로그인에 실패했어요. 잠시 후 다시 시도해 주세요. | 현재 로그인 서비스를 이용할 수 없어요. 잠시 후 다시 시도해 주세요. |

**유지:** 기존 프론트 타임아웃 안내, 실패 후 로그인 화면 복귀, 버튼 재클릭 시 새 인증 시작.
백엔드의 카카오 연결 2초·읽기 3초 설정도 유지한다. 백엔드 수정은 없다.

**확인:** 401·503 각각의 문구 표시, 기존 타임아웃 안내 유지, 이전 인가 코드 재전송 없이 새 로그인 시작.

수정 위치: [login-error.ts](https://github.com/Central-MakeUs/moyeo-client/blob/438dd791c51666e0cd472dbaeb2f02103f701700/apps/web/src/features/social-login/model/login-error.ts)의 `toExchangeErrorReason()`과 `MESSAGES`.
공통 함수는 Apple·네이티브 로그인에도 사용되므로 변경 시 함께 확인한다.

## 2. 카카오 사용자 정보 조회 실패 안내

- 대상: 웹 `POST /api/auth/kakao`, 네이티브 `POST /api/auth/kakao/native`
- 상태: 1번 변경 요청에 통합 / 프론트 미적용

**현재:** 백엔드는 카카오 토큰으로 사용자 ID를 확인한 뒤 회원 DB 처리를 시작한다.
유효하지 않은 토큰은 `401 SOCIAL_LOGIN_FAILED`, 서버 IP 제한·장애·타임아웃·비정상 응답은 `503 SOCIAL_LOGIN_UNAVAILABLE`로 처리한다.

**요청:** 사용자 정보 조회 실패에도 1번의 401·503 안내를 동일하게 적용한다.
프론트는 토큰 교환과 사용자 조회를 별도 호출하지 않으므로 실패 단계를 구분하는 UI는 추가하지 않는다.

**확인:** 웹·네이티브 양쪽에서 401·503 안내가 구분되는지 확인한다.
백엔드 코드·트랜잭션·타임아웃·재시도 흐름은 유지한다.


## 3. 카카오 탈퇴와 연결 정리 응답

- 대상: `DELETE /api/users/me`, 카카오 웹·네이티브 재로그인
- 상태: 백엔드 로컬 검증 완료 / 미배포 / 기존 프론트 성공 흐름 호환, 상세 안내는 후속 개선

**변경:** 모여 DB 탈퇴 후 카카오 연결 해제를 한 번 시도하고, 실패하면 서버가 재시도한다.

| 응답 | 의미 | 프론트 요청 |
| --- | --- | --- |
| 탈퇴 204 | 모여 탈퇴·카카오 연결 해제 완료 | 세션·회원 캐시 정리 후 완료 안내 |
| 탈퇴 202 | 모여 탈퇴 완료·카카오 연결 정리 대기 | 동일하게 세션 정리. 실패가 아닌 정리 중 안내 |
| 로그인 409 `SOCIAL_DISCONNECTION_PENDING` | 이전 탈퇴의 카카오 정리 미완료 | “이전 탈퇴의 연결을 정리 중이에요. 잠시 후 다시 로그인해 주세요.” 안내 |

**호환:** 현재 프론트는 202도 성공으로 받아 세션·캐시 정리 후 로그인 화면으로 이동한다.
409는 기존 로그인 실패 안내로 표시되므로 기존 화면 흐름은 유지된다. 상세 문구 구분은 후속 UX 개선이다.
204·202 문구를 나누려면 응답 본문만 반환하는 공통 Axios 대신 탈퇴 호출부에서 HTTP 상태도 확인할 수 있어야 한다.
재가입을 자동 예약하거나 로그인 요청을 무한 대기시키지 않는다. 정리 완료 후 사용자가 새 인증을 시작한다.
별도 상태 조회·폴링은 추가하지 않는다. Apple 탈퇴 변경은 6번을 참고한다.


## 4. Apple 토큰 교환 실패 안내

- 대상: 웹 `POST /api/auth/apple`, 네이티브 `POST /api/auth/apple/native`
- 상태: 백엔드 수정 / 미배포 / 프론트 미적용

**변경:** Apple이 성공 응답을 반환해도 본문이 비어 있거나 `id_token`이 누락·null·공백이면
기존 401 대신 `503 SOCIAL_LOGIN_UNAVAILABLE`로 처리한다.
유효하지 않은 인증 코드의 401, 외부 장애·타임아웃의 503 처리는 유지한다.

**요청:** 1번의 401·503 안내 구분을 Apple 웹·네이티브에도 동일하게 적용한다.
현재 프론트는 두 상태를 같은 로그인 실패 문구로 표시하므로 기존 화면 흐름은 유지된다.
자동 인증 코드 재전송은 추가하지 않고, 사용자가 새 로그인을 시작하도록 한다.


## 5. Apple 공개키 조회 실패 안내

- 대상: 웹 `POST /api/auth/apple`, 네이티브 `POST /api/auth/apple/native`
- 상태: 백엔드 수정 / 미배포 / 프론트 미적용

**변경:** Apple의 공개키 목록이 비어 있으면 기존 401 대신 `503 SOCIAL_LOGIN_UNAVAILABLE`로 처리하고,
해당 목록은 서버 캐시에 저장하지 않는다. 정상 목록에 토큰의 키가 없으면 기존 401을 유지한다.

**요청:** 4번과 같은 401·503 안내 구분을 적용한다. 공개키 조회는 백엔드 내부 단계이므로
프론트에 별도 API 호출이나 전용 화면은 추가하지 않는다.


## 6. Apple 탈퇴와 연결 정리 응답

- 대상: `DELETE /api/users/me`, Apple 웹·네이티브 재로그인
- 상태: 백엔드 수정 / 미배포 / 기존 프론트 성공 흐름 호환, 상세 안내는 후속 개선

**변경:** 모여 DB 탈퇴와 암호화된 Apple 철회 작업을 함께 저장한 뒤 외부 해제를 한 번 시도한다.
완료 시 204, 재시도가 남으면 202이며 두 응답 모두 세션·회원 캐시를 정리한다.
서버는 작업을 1·2·4분 간격으로 재시도하며 최대 1시간 간격을 유지한다.

**요청:** 3번의 탈퇴 204·202 안내와 로그인 409 `SOCIAL_DISCONNECTION_PENDING` 안내를 Apple에도 적용한다.
자동 정리 중에는 재가입을 보류하고, 완료 후 사용자가 새 Apple 인증을 시작한다.
현재 프론트는 202도 성공으로 처리하므로 기존 화면 흐름과 호환된다.

**예외:** 저장 토큰 누락 시 기존 503·탈퇴 보류를 유지한다. 복호화 실패 시 작업을 유지하고 운영 확인이 필요하다.
수동 해제 안내 기능은 추가하지 않는다. Apple 토큰 필수 조건은 백엔드·DB에서 방어하며 프론트 요청 형식은 유지한다.


## 8. 출발지 수정 후 장소 추천 갱신

- 대상: 회원·게스트 출발지 수정, 장소 조율 현황 조회
- 상태: 백엔드 수정 / 미배포 / 프론트 기존 재조회 흐름 유지

**변경:** 출발지·이동수단 수정 성공 시 저장된 추천을 삭제한다.
다음 장소 현황 조회에서 현재 입력과 계산 조건에 따라 추천을 다시 계산한다.
수정 요청 자체는 카카오를 호출하지 않으며 확정된 장소는 유지한다.

**확인:** 현재 프론트의 출발지 수정 성공 후 장소 현황 캐시 무효화·재조회 흐름을 유지한다.
재계산 실패는 기존 503으로 응답하며, 이전 추천을 다시 반환하지 않는다.
요청·응답 형식과 상태 코드는 유지하고, 새로운 409나 같은 요청 내 자동 재계산은 추가하지 않는다.
